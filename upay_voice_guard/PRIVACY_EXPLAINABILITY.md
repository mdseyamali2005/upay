# T16: Privacy, Synthetic Data & Explainability Statement

## 1. Data Privacy Statement

### 1.1 Data Collection

upay Voice Guard is a **demonstration prototype**. The following data practices apply:

| Data Type | Collected? | Stored? | Duration | Purpose |
|-----------|-----------|---------|----------|---------|
| **Voice audio** | Yes (recording) | No (processed in-memory only) | Duration of STT processing | Intent recognition only |
| **Transcribed text** | Yes (STT output) | Session lifetime only | Discarded at session end | NLU intent classification |
| **PIN entry** | Yes (keypad) | Hashed only (PBKDF2-SHA256) | Persistent | Authentication |
| **Transaction data** | Yes | Persistent (SQLite) | Application lifetime | Balance/history/risk |
| **IP address** | Yes (rate limiting) | In-memory only | 60-second window | Rate limiting / lockout |
| **Session tokens** | Yes | In-memory only | Session lifetime | Authentication |
| **Audit events** | Yes | In-memory only | Last 1,000 entries | Security monitoring |

### 1.2 Data NOT Collected

- ❌ No biometric data (voiceprint, fingerprint)
- ❌ No location data (GPS, cell tower)
- ❌ No device identifiers stored server-side
- ❌ No cross-session user tracking
- ❌ No data shared with third parties (except Gemini API for NLU)

### 1.3 Third-Party Services

| Service | Data Sent | Data Retained by Service | Purpose |
|---------|-----------|-------------------------|---------|
| **Google Gemini API** | Transcribed text (≤500 chars) | Per Google's data policy (may be used for model improvement) | Intent classification & FAQ answers |
| **Microsoft edge-tts** | Response text | Not retained (streaming API) | Text-to-speech generation |
| **Web Speech API** | Voice audio (client-side) | Per browser/Google policy | Speech-to-text (client-side only) |

### 1.4 Data Protection Measures

1. **PIN Security**: Hashed with PBKDF2-HMAC-SHA256 (50,000 iterations) with per-user random salt. Timing-safe comparison (`hmac.compare_digest`).
2. **Input Sanitization**: All user text inputs are sanitized (control characters removed, length limited to 500 chars) before processing.
3. **Prompt Injection Protection**: 13 regex patterns detect and block prompt injection attempts before they reach the LLM.
4. **Network Isolation**: Server only accessible on LAN subnet; CORS restricted to local network IPs.
5. **No Persistent Audio**: Voice recordings are never saved to disk; processed purely in memory for STT.

## 2. Synthetic Data Statement

### 2.1 All Demo Data is Synthetic

**⚠️ IMPORTANT: Every piece of data in this prototype is synthetic and artificially generated.**

| Data Element | Real? | Source |
|-------------|-------|--------|
| User name ("MD. SEYAM ALI") | Synthetic | Hardcoded demo identity |
| Phone number ("01307339929") | Synthetic | Randomly chosen valid-format number |
| PIN ("1234") | Synthetic | Demo-only; labeled in code as "FAKE" |
| Balance (25,000 TK) | Synthetic | Seeded in `db._seed()` |
| Transaction history | Synthetic | Randomly generated by `random.Random(42)` |
| Agent numbers | Synthetic | Random 011xxxxxxxx format |
| Known numbers | Synthetic | Fixed demo numbers |

### 2.2 Intent Dataset

The 85-sample Bangla/Banglish intent dataset (`tests/intent_dataset.json`) was:
- **Manually created** for evaluation purposes
- **Not sourced** from real user conversations
- **Covers**: 17 intent categories × 5 samples each
- **Includes**: Standard Bangla, Banglish (romanized), 6 dialect variants (Sylheti, Chittagong, Noakhali, Rangpur, Barishal, Mymensingh), ASR transcription errors, code-switching

### 2.3 Risk Scoring Training Data

The personalized risk scoring model (`db.get_risk_signals()`) uses:
- **No ML training data** — rules are hand-crafted from domain knowledge
- **5 deterministic signals** based on transaction context (not learned from user behavior)
- **Threshold (0.35)** was set based on domain expertise, not optimized on real data

## 3. Explainability (T16)

### 3.1 Risk Warning Explainability

When the risk scoring engine flags a transaction, the user receives **specific, human-readable explanations** in Bangla:

```
সতর্কতা (ঝুঁকি স্কোর: 55%): নতুন নম্বর — আগে কখনো এই নম্বরে লেনদেন হয়নি।
ব্যালেন্সের 80% — প্রায় সব টাকা তোলা হচ্ছে।
কেউ কি ফোনে আপনাকে টাকা দিতে চাপ দিচ্ছে?
```

**Translation**: "Warning (risk score: 55%): New number — you've never transacted with this number before. 80% of balance — almost all money is being withdrawn. Is someone pressuring you over the phone to send money?"

### 3.2 Risk Factor Descriptions

Each of the 5 risk signals produces a user-facing Bangla explanation:

| Signal | When Triggered | Bangla Explanation |
|--------|---------------|-------------------|
| **Recipient Novelty** | Number not in `known_numbers` | "নতুন নম্বর — আগে কখনো এই নম্বরে লেনদেন হয়নি" |
| **Unusual Amount** | Amount > avg + 2σ | "অস্বাভাবিক পরিমাণ — গড় {avg} টাকার তুলনায় {amount} টাকা অনেক বেশি" |
| **Balance Ratio** | Amount > 50% of balance | "ব্যালেন্সের {pct}% — অর্ধেকের বেশি তোলা হচ্ছে" |
| **Daily Frequency** | ≥2 cash-outs today | "আজই {n} বার ক্যাশ আউট হয়েছে" |
| **Rapid Succession** | Multiple recent cash-outs | "অল্প সময়ে একাধিক ক্যাশ আউট" |

### 3.3 NLU Decision Transparency

The NLU pipeline prioritizes interpretability:

1. **Rule-based NLU runs first**: 82.4% of intents are resolved by explicit keyword matching. The matched keyword is traceable.
2. **LLM used only as fallback**: Gemini is called only when rules produce `unknown`. The raw LLM JSON output is validated against a whitelist.
3. **Injection attempts are logged**: Blocked inputs are recorded in the audit log with `_blocked: injection_detected`.
4. **Combined accuracy is reported**: 98.8% on the 85-sample dataset, with per-intent precision/recall/F1 in `nlu_evaluation_report.md`.

### 3.4 Transaction Decision Audit Trail

Every security-relevant event is logged in the audit system:

| Event | Logged Data |
|-------|-------------|
| `SESSION_START` | session_id, client_ip |
| `AUTH_FAILED` | session_id |
| `REPLAY_BLOCKED` | session_id, duplicate nonce |
| `RATE_LIMITED` | client_ip, path |
| `LOCKOUT` | client_ip, duration |

## 4. Limitations & Responsible AI Acknowledgments

### 4.1 Known Limitations

1. **Keypad entry cannot prevent coercion**: If a user is being physically coerced to enter a PIN or confirm a transaction, the keypad-only security model cannot detect this. The scam warning relies on the user being able to freely say "no."

2. **Voice-based social engineering**: An attacker could potentially trick a user into saying "হ্যাঁ" (yes) at the confirmation step. Mitigation: The system always reads back the full transaction details before confirmation.

3. **Dialect coverage is incomplete**: While the NLU covers 6 major dialect variants, Bangladesh has many more regional speech patterns that may not be recognized.

4. **STT accuracy varies**: Browser-based Web Speech API may have lower accuracy for Bangla dialects compared to Standard Bangla. Production should use a fine-tuned STT model.

5. **LLM hallucination risk**: Gemini may occasionally classify intent incorrectly. Mitigation: Rule-based NLU handles the majority of cases; LLM output is whitelist-validated; LLM never directly triggers financial actions.

### 4.2 Responsible AI Principles Applied

| Principle | Implementation |
|-----------|---------------|
| **Safety** | LLM is sandboxed to classification only; never moves money |
| **Fairness** | NLU supports 6+ dialects; tested for equal accuracy across variants |
| **Privacy** | No audio stored; no biometrics; synthetic demo data |
| **Transparency** | Risk factors shown to user in native language; NLU pipeline is auditable |
| **Accountability** | Audit log tracks all security events; test suite validates safety properties |
| **Human control** | User must confirm every step; can cancel at any point; human escalation path (16268) |
